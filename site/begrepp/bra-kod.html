PRAO på ITS

Bra kod

Tumregler som programmerare på ITS använder. De är vägledning, inte lagar.

Huvudidén

Hitta det som kommer att ändras, och håll det åtskilt från resten.

Nästan alla tumregler nedan är olika sätt att följa den idén.

Håll det enkelt (KISS)

Välj den enklaste lösningen som fungerar. Smart kod som ingen förstår är dålig kod, även om den fungerar.

Bygg inte i förväg (YAGNI)

You Aren't Gonna Need It. Bygg det du behöver nu, inte det du kanske behöver sedan. Innan du lägger till något, fråga: Vilket problem löser det just nu? Om svaret är "kanske en dag" kan du vänta.

Den här regeln går före alla andra.

Upprepa dig inte (DRY)

Samma sak ska stå på ett ställe. Kopierar du samma rader tre gånger: gör en funktion av dem. Då räcker det att rätta en gång.

Men försiktigt: två saker som bara råkar se lika ut behöver inte slås ihop.

En sak per del

En funktion eller fil ska ha ett skäl att ändras. Fråga dig: vem eller vad kan göra att jag behöver ändra den här koden? Om svaret är flera orelaterade saker, dela upp.

// Gör för mycket
function uppdateraSpelet() { /* flytta, rita, räkna poäng, spela ljud */ }

// Bättre
function flyttaSpelare() { ... }
function ritaSpelare() { ... }
function raknaPoang() { ... }

Lägg det som ändras i data

Gör det lätt att ändra sådant som ofta ändras, utan att röra logiken.

// Svårt: ny färg kräver ny kod
if (fiende === "röd") { ... } else if (fiende === "blå") { ... }

// Lättare: ny färg kräver bara en ny rad i listan
const fiendeHastighet = { röd: 3, blå: 5, grön: 2 };

Ta emot det du behöver

En funktion ska få de värden den behöver som parametrar, i stället för att plocka dem från allt möjligt utanför.

// Kräver att hela spelet finns
function ärTräff() { return spel.spelare.x === spel.fiende.x; }

// Behöver bara två tal
function ärTräff(spelareX, fiendeX) { return spelareX === fiendeX; }

Den andra går att testa med två tal. Den första går bara att testa med ett helt spel.

Lukter i koden

En kodlukt är ett tecken på att något kan behöva förbättras. Det är inte ett fel, men en varningsflagga.

  • En mycket lång funktion eller fil som gör allt.
  • Samma kod på flera ställen.
  • Siffror och texter utspridda utan förklaring, som if (x > 640).
  • Namn som a, tmp och data2.

Ge saker namn som säger vad de är: spelarX är bättre än x.

Städa utan att ändra beteendet

Att refaktorera betyder att göra koden bättre inuti utan att ändra vad den gör utåt.

  1. Kontrollera att allt fungerar innan du börjar.
  2. Gör en liten förbättring.
  3. Testa igen. Fungerar det fortfarande? Annars ångra.
  4. Spara och gör nästa förbättring.

Omdöme är viktigast

Reglerna är verktyg. I ett litet projekt kan det vara helt rätt att inte använda en regel. Att kunna säga jag känner till den här regeln men den behövs inte här, och det är därför visar mer förståelse än att följa alla regler blint.
